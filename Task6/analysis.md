# Отчёт по результатам анализа Kubernetes Audit Log

## Подозрительные события

1. **Создание namespace secure-ops**:
   - Кто: `minikube-user` (группы: `system:masters`, `system:authenticated`)
   - Где: Создание нового namespace
   - Почему подозрительно: Создание изолированного namespace может быть первым шагом для скрытия malicious activity

2. **Создание Service Account monitoring**:
   - Кто: `minikube-user`
   - Где: namespace `secure-ops`
   - Почему подозрительно: Создание специального service account может указывать на подготовку к несанкционированному доступу

3. **Попытка доступа к секретам**:
   - Кто: `system:serviceaccount:secure-ops:monitoring`
   - Где: namespace `kube-system`
   - Почему подозрительно: Попытка доступа к default-token в системном namespace без соответствующих прав

4. **Создание привилегированных подов**:
   - Кто: `minikube-user`
   - Где: namespace `secure-ops`, pod `privileged-pod`
   - Комментарий: Создан pod с `securityContext.privileged: true`, что позволяет escape из контейнера и получить доступ к хостовой системе

5. **Использование kubectl exec в системном поде**:
   - Кто: `minikube-user`
   - Что делал: Выполнил команду `cat /etc/resolv.conf` в CoreDNS pod в namespace `kube-system`
   - Почему подозрительно: Получение доступа к системным конфигурационным файлам

6. **Попытка удаления audit-policy**:
   - Кто: Пользователь `admin`
   - Возможные последствия: Попытка отключения аудита для сокрытия malicious activity
   - Результат: Неуспешная попытка (файл не найден по указанному пути)

7. **Создание RoleBinding с правами cluster-admin**:
   - Кто: `minikube-user`
   - К чему привело: ServiceAccount `monitoring` получил права `cluster-admin`
   - Уровень угрозы: КРИТИЧЕСКИЙ - полный контроль над кластером

## Вывод

Обнаружена цепочка атак, направленная на получение полного контроля над Kubernetes кластером. Злоумышленник последовательно:

1. Создал изолированное пространство для операций
2. Подготовил service account для дальнейшего использования
3. Пытался получить доступ к системным секретам
4. Создал привилегированный контейнер для потенциального escape
5. Исследовал системные конфигурации
6. Пытался отключить аудит для сокрытия активности
7. Предоставил service account права cluster-admin

Рекомендации по реагированию:
1. Немедленно отозвать права cluster-admin у serviceaccount:secure-ops:monitoring
2. Удалить namespace secure-ops и все связанные ресурсы
3. Проверить все привилегированные поды в кластере
4. Пересмотреть RBAC политики и ограничить права пользователя minikube-user
5. Внедрить Pod Security Admission для запрета привилегированных подов
6. Усилить мониторинг и аудит кластера
7. Проверить системные логи на предмет других suspicious activities
