# Требования к интеграциям с внешними системами

## 1. Общие требования регуляторов


### 1.1. Обработка персональных данных (ФЗ-152)
- Получение явного согласия субъектов на обработку ПДн
- Обеспечение конфиденциальности и безопасности ПДн при передаче и хранении
- Ограничение доступа к ПДн на основе принципа минимальных привилегий
- Ведение журналов учета операций с ПДн

### 1.2. Обработка биометрических данных (ст. 11 ФЗ-152)
- Отдельное согласие на обработку биометрических данных
- Хранение биометрических шаблонов (не исходных изображений)
- Сертификация средств защиты биометрических данных ФСТЭК России
- Запрет на передачу биометрических данных третьим лицам без согласия


## 2. Требования к интеграциям по системам

### 2.1. Платёжная система


**Тип данных:** Финансовые транзакции, персональные данные

**Требования безопасности:**
- Соответствие стандарту PCI DSS уровня 1
- Двухфакторная аутентификация для операций с деньгами
- Шифрование данных при передаче (TLS 1.3) и хранении (AES-256)
- Регулярный аудит безопасности и penetration testing

**Протоколы взаимодействия:**
- Основной: REST API с OAuth 2.0 client credentials
- Резервный: SFTP для batch-обработки платежей
- Аутентификация: mTLS + JWT с ограниченным временем жизни

**Особые требования:**
- Подтверждение операций через мобильное приложение для сумм свыше 15 000 руб.
- Ежедневное сверка балансов и транзакций
- Механизм возврата платежей (refund) 


### 2.2. Поставщик ресурсов ЖКХ


**Тип данных:** Персональные данные, финансовые начисления

**Требования безопасности:**
- Шифрование передаваемых данных (TLS 1.2+)
- Валидация входящих данных для предотвращения инъекций
- Контроль целостности передаваемых данных (цифровая подпись)

**Протоколы взаимодействия:**
- Основной: REST API с API-key аутентификацией
- Альтернативный: SOAP/XML для legacy-систем
- Формат данных: JSON с схемой validation

**Особые требования:**
- Ежедневная синхронизация данных по начислениям
- Механизм обработки расхождений в данных
- История изменений для аудита
- Уведомления об изменении тарифов за 30 дней


### 2.3. Гос. регистрационные органы


**Тип данных:** Персональные данные, данные о недвижимости

**Требования безопасности:**
- Соответствие требованиям СМЭВ 3.0
- Использование квалифицированной электронной подписи
- Шифрование канала связи (ГОСТ 28147-89)
- Сертифицированные средства криптографической защиты информации

**Протоколы взаимодействия:**
- Обязательный: SOAP/XML через СМЭВ
- Аутентификация: ГОСТ Р 34.10-2012 электронная подпись
- Формат данных: XML со схемой XSD

**Особые требования:**
- Соответствие ФЗ-210 "О порядке рассмотрения обращений граждан"
- Срок обработки запросов - не более 5 рабочих дней
- Механизм отслеживания статуса запросов
- Архивация всех исходящих и входящих сообщений на 5 лет


### 2.4. Интеллектуальный домофон


**Тип данных:** Биометрические данные, журналы доступа

**Требования безопасности:**
- Сертификация ФСТЭК России для обработки биометрии
- Локальное хранение биометрических шаблонов (не изображений)
- Шифрование передаваемых биометрических данных
- Физическая защита устройств от несанкционированного доступа

**Протоколы взаимодействия:**
- Основной: MQTT с TLS шифрованием
- Резервный: REST API для управления
- Аутентификация: Certificate-based (X.509 certificates)

**Особые требования:**
- Согласие на обработку биометрии для каждого пользователя
- Возможность удаленного отзыва прав доступа
- Локальное кеширование команд на случай потери связи
- Журналирование всех событий доступа с retention 1 год


### 2.5. Интеллектуальный шлагбаум


**Тип данных:** Номера автомобилей, журналы доступа

**Требования безопасности:**
- Шифрование передаваемых данных (TLS 1.2+)
- Защита от spoofing номерных знаков
- Контроль целостности прошивки устройств

**Протоколы взаимодействия:**
- Основной: MQTT с TLS шифрованием
- Альтернативный: REST API для статистики
- Аутентификация: API-key + device certificate

**Особые требования:**
- Интеграция с системой распознавания номеров
- Настройка правил доступа по времени и дням недели
- Уведомления о несанкционированных попытках доступа
- Automatic blacklisting при multiple failed attempts


## 3. Общие требования ко всем интеграциям


### 3.1. Мониторинг и observability
- Логирование всех входящих/исходящих запросов
- Метрики latency, error rate, throughput
- Health checks для мониторинга доступности
- Alerting при недоступности систем более 5 минут

### 3.2. Обработка сбоев
- Retry механизм с экспоненциальной backoff-стратегией
- Circuit breaker для избежания каскадных сбоев
- Dead letter queue для неуспешных сообщений
- Механизм ручного повторения обработки

### 3.3. Безопасность
- Регулярный аудит безопасности интеграций
- Обновление сертификатов и ключей (rotation)
- Проведение penetration testing не реже 1 раза в год
- Соответствие требованиям ФСТЭК России и ФСБ России
